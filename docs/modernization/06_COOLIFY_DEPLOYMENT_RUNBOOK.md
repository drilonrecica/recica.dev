# 06 — Coolify Deployment Runbook

## 1. Infrastructure facts

Current environment:

- Hetzner VPS
- Coolify
- Coolify Caddy proxy
- Cloudflare-proxied public domains
- separate Coolify resources for Recica, Tools, and Labs

This runbook preserves that model.

## 2. `recica.dev` Coolify configuration

### Keep

- build pack: Nixpacks
- base directory: `/recica` or the equivalent current app directory
- static-site option: enabled
- publish directory: `dist`
- domain: `https://recica.dev`
- Cloudflare proxy: enabled

### Change during toolchain phase

- package manager: pnpm
- build command: `pnpm build`
- Node build version: 24 LTS
- lockfile: `recica/pnpm-lock.yaml`

### Environment

Recommended:

```text
PUBLIC_INDEXING_ENABLED=true
```

Use the app's chosen Astro-compatible variable naming if public-prefix semantics require it.

Preview resource:

```text
PUBLIC_INDEXING_ENABLED=false
```

No runtime secrets are needed.

### Verify

```bash
curl -I https://recica.dev/
curl -I https://recica.dev/about
curl -I https://recica.dev/robots.txt
curl -I https://recica.dev/sitemap-index.xml
```

Confirm the actual sitemap filename generated by Astro.

## 3. Tools Coolify configuration after migration

### Keep

- Dockerfile build pack
- base directory: `/tools`
- domain: `https://tools.recica.dev`
- independent resource
- Cloudflare proxy enabled

### Change

- Dockerfile becomes static build/runtime
- exposed port changes from Node's 3000 to static server port, normally 8080
- health check targets `/health` or `/`
- remove obsolete Node runtime environment variables
- indexing variables become build arguments/environment available during build

### Build variables

Production:

```text
PUBLIC_SITE_URL=https://tools.recica.dev
PUBLIC_INDEXING_ENABLED=true
```

Preview:

```text
PUBLIC_SITE_URL=https://tools.recica.dev
PUBLIC_INDEXING_ENABLED=false
```

The production canonical remains production even in previews.

### Runtime variables

Ideally none.

A static site should not depend on runtime environment variables.

### Resource limits

Initial conservative runtime settings:

- memory: 128 MiB limit
- CPU: 0.25 core
- no persistent storage

After observing stable usage, 64 MiB may be enough. Do not impose a limit that causes the web server or health checks to be killed.

## 5. Reference static Dockerfile

This is a design reference, not a substitute for validating current image versions and repository paths.

```dockerfile
FROM node:24-alpine AS build

ENV PNPM_HOME="/pnpm"
ENV PATH="$PNPM_HOME:$PATH"

RUN corepack enable
WORKDIR /app

COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

FROM nginxinc/nginx-unprivileged:stable-alpine AS runtime

COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/build /usr/share/nginx/html

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget -q -O /dev/null http://127.0.0.1:8080/health || exit 1
```

Hardening refinements:

- pin tested image digests
- use build cache mounts if supported and worthwhile
- ensure runtime user is non-root
- ensure the final image contains no package manager or source
- verify `wget` exists before relying on it
- use a static-server image version supported by dependency automation

Do not add `node_modules` to the final stage.

## 6. Reference Nginx configuration

Validate generated route filenames before adopting this verbatim.

```nginx
server {
    listen 8080;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    server_tokens off;
    autoindex off;

    location = /health {
        default_type text/plain;
        add_header Cache-Control "no-store" always;
        return 200 "OK\n";
    }

    location /_app/immutable/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable" always;
    }

    location = /robots.txt {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=0, must-revalidate" always;
    }

    location = /sitemap.xml {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=0, must-revalidate" always;
    }

    location / {
        try_files $uri $uri.html $uri/ =404;
        add_header Cache-Control "public, max-age=0, must-revalidate" always;
    }

    error_page 404 /404.html;

    add_header Content-Security-Policy "frame-ancestors 'none'" always;
    add_header X-Frame-Options "DENY" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "camera=(), geolocation=(), microphone=(), payment=(), usb=()" always;
}
```

Important:

- avoid a full Nginx CSP that conflicts with SvelteKit's hash-based prerendered meta CSP
- test whether `404.html` exists
- test clean URLs
- add MIME/compression behavior as supported by the selected image
- avoid `try_files ... /index.html` SPA fallback
- ensure headers apply to error responses using `always`

### HSTS

Choose one authoritative layer:

- Cloudflare
- Coolify Caddy
- app Nginx

Do not enable HSTS preload casually.

Before adding `includeSubDomains`, confirm every relevant subdomain is permanently HTTPS.

## 7. Cloudflare guidance

Recommended:

- SSL/TLS mode: Full (strict)
- Always Use HTTPS: enabled
- proxy enabled
- Brotli/compression enabled
- respect origin cache headers unless a deliberate rule overrides them
- no injected analytics
- no third-party optimization feature that rewrites scripts unexpectedly
- no blanket HTML cache-forever rule
- cache immutable assets aggressively
- ensure deployment purges/updates HTML correctly

Review:

- Rocket Loader or equivalent script rewriting should normally remain disabled
- email-obfuscation/script injection should be tested against CSP
- browser integrity/caching features should not alter tool output
- WAF rules should not block static assets or webmaster crawlers

Agents cannot assume access to Cloudflare settings. Document required human changes.

## 8. Deployment checklist for Tools/Labs

Before first static deployment:

- static build succeeds
- all routes generated
- local Nginx container starts
- health check passes
- no Node process is required
- route E2E passes against container
- unknown route returns 404
- robots/sitemap correct
- preview is noindex
- production is indexable
- final headers correct
- Cloudflare does not break CSP
- image scan passes

During deployment:

- deploy preview or temporary resource first
- compare representative route HTML
- compare tool outputs
- compare headers
- compare redirects
- monitor health
- keep previous deployment available

After production:

```bash
curl -fsS https://tools.recica.dev/health
curl -I https://tools.recica.dev/
curl -I https://tools.recica.dev/json
curl -I https://tools.recica.dev/does-not-exist
curl -fsS https://tools.recica.dev/robots.txt
curl -fsS https://tools.recica.dev/sitemap.xml
```

Repeat for Labs.

Expected unknown-route status: `404`, not `200`.

## 9. Rollback runbook

If static migration fails:

1. use Coolify rollback to the previous healthy deployment
2. restore the old exposed port if configuration changed
3. restore old health path if configuration changed
4. confirm Cloudflare origin health
5. capture failure details
6. fix in a new commit
7. rerun preview verification

Do not delete the previous deployment before the new deployment has passed production smoke tests.

---

## 10. Operational monitoring without analytics

Allowed:

- Coolify health status
- container CPU/memory
- uptime checks
- HTTP status monitoring
- server error logs
- Cloudflare security/availability metrics
- Search Console/Bing Webmaster Tools

Prohibited:

- logging request bodies
- logging query strings containing user input
- browser session replay
- user fingerprinting
- tool-operation telemetry

Static Tools/Labs should produce very little application-level log data because no application server remains.
